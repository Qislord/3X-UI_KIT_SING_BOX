# BackupFix.md — надёжный бэкап и перенос сервера (новый домен, новый IP)

> Ревью `kit backup` / `kit restore` (`scripts/kit.sh`) и план переделки.
> Главный сценарий — **переезд на новый VPS с другим доменом и другим IP**.
> Ошибка этой версии плана в первом черновике («восстановить всё из архива») разобрана в §1.

## 1. Главное: окружение нельзя тащить на другой сервер

В архиве лежат не только «данные», но и **привязки к старому серверу**. Если развернуть их на
новом VPS — сервер, скорее всего, «полетит» или будет вести клиентов на старый адрес:

| Что в архиве | К чему привязано | Что будет на новом сервере, если просто восстановить |
|---|---|---|
| `kit.env` → `HOST` | IP старого сервера | ссылки/QR/портал укажут на **старый IP** |
| `kit.env` → `DOMAIN/WS_DOMAIN/WEB_DOMAIN` | старые домены | подписка и панель на **старом домене** |
| `externalProxy`/SNI внутри `x-ui.db` | старые домены | все ссылки ведут на **старый домен** |
| `install-result.env` | порт/путь/API-токен **старого** экземпляра панели | рассинхрон с портом панели на новом сервере |
| Let's Encrypt сертификаты | старый домен | недействительны; панель/nginx не поднимутся |
| `nginx/kit.conf`, `kit-stream.conf` | старые домены + пути к сертификатам | «чужой» конфиг, сайт/подписка ломаются |
| `subURI`/`SUB_BASE` | старый домен | подписка недоступна |

**Вывод: переносить нужно только «данные», а окружение всегда создавать заново установщиком
под новые домены/IP.** Это и есть гарантия, что новый сервер не полетит.

## 2. Что «данные», а что «окружение»

**Данные (переносим):**
- список пользователей: `email`, `subId`, лимит трафика, срок, число устройств, вкл/выкл;
- к каким протоколам привязан пользователь (для повторной привязки на новом сервере);
- аккаунты личного кабинета: логин, хеш+соль пароля (PBKDF2, `internal/auth/auth.go`), `sub_token`,
  `is_active` — **пароли продолжают работать**, менять их не нужно.

**Окружение (НЕ переносим, создаётся установщиком):**
- домены, `HOST`/IP, сертификаты, nginx, порт/путь/токен панели, `subURI`, ключи инбаундов,
  `externalProxy`, SNI.

Замечание: `sub_id`/`sub_token` — это просто идентификаторы, они не привязаны к домену, поэтому их
переносим, чтобы связать аккаунт кабинета с новым клиентом.

## 3. Надёжный сценарий переезда (новый домен, новый IP)

**Шаг 1. На новом VPS — обычная свежая установка с НОВЫМИ доменами/IP:**

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Qislord/3X-UI_KIT_SING_BOX/main/scripts/3x-ui.sh) \
  --domain new-domain.com \
  --ws-domain ws.new-domain.com \
  --protocols reality,ws,vmess
```

Установщик создаёт **согласованное** окружение под новый сервер: домены, сертификаты, nginx,
панель, личный кабинет. Тут ничего из архива не подмешивается.

**Шаг 2. Перенос данных из архива (режим «импорт»):**

```bash
scp root@OLD_IP:/root/kit-backup-*.tar.gz .
# на новом сервере:
kit restore --import /root/kit-backup-2026-01-01-1200.tar.gz
```

`kit restore --import`:
1. Читает из архива **пользовательский манифест** (см. §5) и БД кабинета.
2. Через API **новой** панели пересоздаёт пользователей: `email`, `subId`, лимиты, срок,
   число устройств, вкл/выкл, и привязывает их к новым инбаундам по названию протокола
   (совпадающие с тем, что было у пользователя).
3. Вливает аккаунты кабинета (логин + хеш пароля + `sub_token`) в новую `portal.db`.
4. **Ничего не трогает** в доменах, сертификатах, nginx и настройках панели.
5. Печатает отчёт: сколько пользователей перенесено, что пропущено, что осталось сделать.

**Шаг 3. Раздать пользователям новую подписку.** Ссылки **обязаны измениться** (новый домен), поэтому
пользователи один раз обновляют подписку в приложении — пароли кабинета и лимиты при этом те же.

---

## 4. Если меняется только IP (домен тот же) — отдельный режим

Тогда `externalProxy`/домены валидны, и можно сохранить ключи. Но на новом сервере новый порт/токен
панели, поэтому «тащить» старый `install-result.env` нельзя без согласования с БД.

- Рекомендуется тот же `--import` (надёжно, ключи пересоздаются).
- «Продвинутый» режим `kit restore --full` (для восстановления на **тот же** сервер/конфигурацию):
  восстанавливает данные + окружение как есть, с явным предупреждением, что домен/IP должны
  совпадать, и с правкой `HOST`. Сертификаты Let's Encrypt, если их на сервере не осталось,
  перевыпускаются вручную. Смена домена через `--full` **запрещена** — для этого `--import`.

## 5. Что и как менять в коде

### `kit backup` (`scripts/kit.sh:942-978`)

1. **Портативный манифест.** Дополнительно к снимкам баз сохранять `backup/users.json` —
   плоский список пользователей, полученный через `clients/list` (сервер в момент бэкапа живой):
   ```json
   [{"email":"sasha","subId":"...","totalGB":0,"expiryTime":0,"limitIp":3,
     "enable":true,"protocols":["REALITY","VLESS-WS","Hysteria2"]}]
   ```
   `protocols` — remarks инбаундов, к которым привязан пользователь (из `inboundIds`).
2. **Снимок `portal.db` через SQLite backup API** и выгрузка аккаунтов кабинета в
   `backup/portal_accounts.json` (username, password_hash, salt, sub_id, sub_token, is_active).
3. Манифест (`backup/manifest.env`): `BACKUP_KIT_VERSION`, `BACKUP_DATE`, старые домены, старый
   `HOST`, список протоколов, число пользователей. Нужен для проверки и отчёта при восстановлении.
4. Не удалять текущие бэкапы баз — они нужны для режима `--full` (восстановление на тот же сервер).

### `kit restore` (`scripts/kit.sh:980-1030`) — переработать

- **Режим по умолчанию `--import`** (безопасный, для переезда): только данные, никакого окружения.
- `--full` — восстановление окружения (для того же сервера); с проверкой совпадения домена и
  предупреждением; перевыпуск сертификатов, правка `HOST`.
- `--check <архив>` — dry-run: показать манифест и что будет сделано, ничего не менять.
- `--host IP` — переопределить `HOST` при `--full`. Смена домена через `--full` запрещена
  (реализовано): она разъедет `kit.env` и nginx — для нового домена только `--import`.
- Перед импортом: проверить, что панель доступна (иначе: «сначала установите сервер»).
- Идемпотентность: существующих пользователей/аккаунты не дублировать (обновлять лимиты).
- Читать `manifest.env`, сверить версию kit; явный отчёт вместо «всё сохранено».

### `kit check` — добавить проверки

- аккаунты кабинета ссылаются на `subId`, которые есть в панели;
- порт/путь/токен из `install-result.env` совпадают с настройками панели;
- файлы сертификатов из конфигов существуют.

### Порядок восстановления (важно)

При `--full` восстанавливать `install-result.env` **до** старта `x-ui`, чистить `-wal`/`-shm`,
делать `PRAGMA integrity_check`, выставлять права `600`.

---

## 6. Почему так надёжно

1. Новый сервер **всегда** получает своё окружение от установщика под свои домены/IP — в него
   физически не может попасть старый домен/IP/сертификат.
2. Переносятся только данные, не имеющие привязки к домену (пользователи, лимиты, аккаунты).
3. Пароли кабинета продолжают работать (переносим хеш+соль, а не сам пароль).
4. `subId` переносится вместе с клиентом — аккаунт кабинета и подписка остаются связанными.
5. Ссылки меняются осознанно (новый домен) — это ожидаемо и безопасно.

Итог: `kit restore --import` **не может** увести клиентов на старый адрес или сломать nginx, потому
что вообще не касается окружения.

## 7. Чек-лист проверки (два сервера, разные домены)

На **A** (старый):
- [ ] `kit user add sasha --gb 5 --days 30`, `kit user attach sasha hy2`.
- [ ] Второй пользователь выключен: `kit user off vasya`.
- [ ] Записать `kit user list` и пароль/логин кабинета.
- [ ] `kit backup` → `scp` архив.

На **B** (новый, новые домены):
- [ ] Свежая установка `3x-ui.sh --domain new... --protocols reality,ws,vmess`.
- [ ] `kit restore --import /root/kit-backup-*.tar.gz`.
- [ ] `kit user list` — те же пользователи, лимиты, срок, статус.
- [ ] Вход в кабинет СТАРЫМ паролем работает.
- [ ] Подписки (universal, sing-box, Clash) открываются, ссылки — на **новый** домен.
- [ ] Каждый перенесённый протокол реально подключается.
- [ ] `kit sync-`/`kit check` не находит рассинхрона `subId` ↔ аккаунты.
- [ ] В архиве **не осталось** ни одной ссылки на старый домен (проверка `grep` по выдаче).
